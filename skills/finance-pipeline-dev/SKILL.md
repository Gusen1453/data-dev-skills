# 金融投研数据管道开发

服务券商与基金的分析师、研究员和给他们供数的人。默认假设：**管道没有文档或文档已过时，调度配置与代码不符，没有现成的对账机制**。任务顺序：先摸清更新制度与现状，再定方案。摸现状 → 定更新制度 → 定增量 → 定幂等 → 定回补 → 定重跑恢复 → 交付。

## 这个 skill 交付什么

用户给管道设计或排障需求，你产出四样东西：

1. **管道设计** `pipeline.md`：每段管道的源/目标、增量策略、幂等语义、回补方案、重跑与恢复、调度依赖、SLA。
2. **可执行脚本/配置** `pipelines/`：按引擎与调度系统原生格式（`.sql`/`.py`/DAG 配置），参数化窗口，**默认只产出，不直接跑生产任务**。
3. **管道契约** `pipeline.yaml`：源/目标、更新制度、频率、SLA、依赖、幂等声明——引用 DDL 产出的 `contract.yaml`，并作为 `finance-data-qc` 时效检查的 `CONFIRMED` 前提。
4. **排障报告**（排障场景）：根因定位、证据等级、修复建议。

管道设计与契约是交付物；探索过程必须可追溯、可重跑。

## 怎么用这份 skill（路由总览）

SKILL.md 只给流程骨架和分发规则。具体方法在 `references/` 下，**按触发条件按需加载，不要一次全读**。

| 阶段 | 动作 | 何时加载哪份 reference |
|---|---|---|
| 0 边界 | 确认源/目标表、更新制度、SLA、交付物（设计/脚本/排障）、执行权限 | 无需 reference |
| 1 摸现状 | 读 DDL 产出的 contract.yaml、现有管道定义、目标表结构（分区/键/时态列） | 无需 reference；未知口径回 DDL skill |
| 2 定更新制度 | 判定实时/T+1 定点/披露驱动/定期发布 | **必读** `references/incremental.md` 第一节 |
| 3 定增量 | 按制度与源能力选水位线/CDC/分区覆盖/全量 | `references/incremental.md` |
| 4 定幂等 | 目标键 + 原子写 + 去重，失败重跑结果一致 | **必读** `references/idempotency.md` |
| 5 定回补 | 窗口参数化、并发限速、幂等重放 | `references/backfill.md` |
| 6 定重跑恢复 | checkpoint、重试、死信、对账、SLA 告警 | `references/rerun-recovery.md` |
| 7 交付 | 产出 pipeline.md + pipelines/ + pipeline.yaml | `references/pipeline-contract.md` |

更新制度与目标表键、分区来自 DDL 契约；契约缺失时先回 `using-data-dev` 走 DDL 责任补契约，或按待确认处理。

## 硬性规范

1. **审查只读。** 排查与设计阶段只用只读访问；不直接改生产调度、不直接跑生产任务，除非用户对具体操作明确批准。
2. **预算先行。** 审查查询限定范围与上限；禁止无界扫描。
3. **幂等是默认要求。** 交付的管道脚本必须可重复执行且结果一致；无法做到的要显式声明并说明风险。
4. **参数化窗口。** 回补与重跑脚本禁止硬编码一次性日期，一律 `--from/--to` 或等价参数。
5. **证据分级。** 探索观察标 `OBSERVED`，语义推断标 `INFERRED`；更新制度与 SLA 只有用户确认或带版本规范支持才能标 `CONFIRMED` 并写进契约。
6. **破坏性操作需批准。** 清空分区、覆盖生产数据、删表、改调度：先给脚本与影响面，获批后执行。
7. **原生格式交付。** 脚本按目标引擎与调度系统原生可执行格式保存，不把非 SQL 伪装成 `.sql`。

## 执行流程

1. **确认边界。** 记录源/目标表、更新制度（或待确认）、SLA、交付物、执行权限。
2. **摸现状。** 读 contract.yaml（键/分区/时态列）、现有管道定义（调度 DAG/cron/脚本）、目标表结构；未确认的口列入待确认清单。
3. **定更新制度。** 用 `incremental.md` 第一节对齐 QC 的四种制度（实时/T+1 定点/披露驱动/定期发布）；制度未确认不写 SLA。
4. **定增量。** 按制度与源能力选策略：时间水位线、CDC、分区覆盖、全量快照；写明晚到与修订的处理。
5. **定幂等。** 按目标键与分区定原子替换/去重/upsert；失败中间态如何清理。
6. **定回补。** 窗口参数化、按分区并行、限速与上游就绪检查。
7. **定重跑恢复。** checkpoint 与恢复点、重试策略、死信、对账、SLA 告警。
8. **交付。** 产出 `pipeline.md`、`pipelines/` 脚本、`pipeline.yaml`；自检硬性规范。
9. **与 QC 衔接。** 把更新制度、应到未到窗口、链路时间戳写进 `pipeline.yaml`，供 `finance-data-qc` 的 freshness 检查消费。

正反例见 `examples/few-shots.md`。

## 交付物要求

- **管道设计** `pipeline.md`：每段管道的源/目标、增量方式、幂等语义、回补策略、重跑恢复、SLA、依赖、待确认清单。
- **脚本** `pipelines/`：原生可执行，窗口参数化，不硬编码一次性快照；带稳定 `pipeline_id` 与版本号。
- **管道契约** `pipeline.yaml`：结构见 `references/pipeline-contract.md`；未知项显式 `null`，不默认套用其他市场的制度。
- **排障报告**（排障场景）：根因假设的证据等级、反证条件、修复建议；未确认根因不写结论。

## 必须停下的情况

- 连接信息里有明文口令、私钥或会被写进交付物的令牌。
- 只有写权限账号可用，无法建立只读审查边界。
- 任务要求直接在生产环境跑破坏性操作（清分区、覆盖、删表、改调度），未获用户对具体操作的明确批准。
- 无法确认源或目标结构，写不出可验证的增量/幂等方案。
- 更新制度与 SLA 无法确认，却要求写死进契约。
- 排障查询无法限定范围，可能形成无界扫描。
- 需求实质是建表、质检、查询接口、治理或合规的最终结论：保存观察，回到 `using-data-dev` 选对应责任。
