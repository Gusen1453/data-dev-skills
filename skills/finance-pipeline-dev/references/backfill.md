# 回补

回补是把历史窗口重新算一遍（上游补数据、口径修订、首次上线补历史）。原则：**窗口参数化、幂等重放、并行受限、上游就绪才动手**。

## 原则

1. **窗口参数化。** 一律 `--from <date> --to <date>` 或等价参数，禁止硬编码日期；同一个回补脚本可重放任意窗口。
2. **幂等重放。** 同一窗口可反复执行且结果一致（见 `idempotency.md`）；回补用的就是重跑能力，非幂等的回补只会放大问题。
3. **按分区并行，限速执行。** 按目标分区粒度并行；对上游与目标库设并发与配额上限，避免回补打爆在线链路。
4. **上游就绪检查。** 回补窗口的上游数据必须已到位（上游覆盖起点、可得时间）；先查上游再动手，否则回补出一片"看起来有数其实是缺的"。

## 窗口判定

- **交易日历 vs 自然日**：窗口按目标表的日历切（交易日历表或 `contract.yaml` 的 `frequency`）；宏观按发布日历，披露驱动按披露日。
- **与增量水位线不重叠**：回补窗口与增量窗口边界明确，回补完成后水位线前移，避免双写。
- **晚到窗口**：回补不覆盖仍在晚到容忍期内的窗口，否则会被后续晚到数据反复改写；晚到容忍期过后再回补定稿。

## 优先级

| 场景 | 先补什么 |
|---|---|
| 首次上线补历史 | 消费方要求的覆盖起点（回测比取数要求长得多）→ 影响面最大的标的/窗口 |
| 上游补数 | 补数通知中明确的窗口 → 当前应到未到的缺口 |
| 口径修订 | 修订生效日之后的所有窗口 → 修订前的历史按"当时可见"保留（见 `incremental.md`） |

## 回补后对账

- 每个回补窗口跑完即对账：行数、主键唯一性、关键金额合计，与上游或历史基线比对。
- 回补结果记录：窗口、版本、执行时间、对账结果，供 QC 追溯（"昨天核对过的数字今天变了"要能解释）。

## 反例

- 回补脚本里写死 `2024-01-01`：换窗口要改代码。
- 上游还没补完就回补：目标表出现"部分窗口有值"，质检误判断档。
- 回补不幂等：重放一次多一行。
