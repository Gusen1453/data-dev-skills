# 金融投研建表与 DDL 设计

服务券商与基金的分析师、研究员和给他们供数的人。默认假设：**没有成文规范或规范已过时，库表注释不可信，现有库的"惯例"只算观察不算事实**。任务顺序：先摸清现有库，再动手。探索 → 提取惯例 → 对照规范 → 设计 → 写 DDL → 交付契约。

## 这个 skill 交付什么

用户给建表或改表需求，你产出四样东西：

1. **惯例清单** `conventions.md`：探索现有库得到的命名、类型、键、分区、注释观察，逐条标证据等级与依据。
2. **建表 DDL** `.sql`：按引擎方言生成，带注释、约束、分区、索引；兼容迁移优先；**默认只产出脚本，不执行**。
3. **设计说明** `design.md`：每张表的用途、主键、时态语义、单位/时区、复权口径、与现有表的关系。
4. **数据契约** `contract.yaml`：字段语义契约，与 `finance-data-qc` 的验收契约同构，作为后续质检的 `CONFIRMED` 口径来源。

DDL 和契约是交付物；探索过程必须可追溯、可重跑。

## 三层规范：硬性、惯例、待确认

写任何 DDL 前先分层：

- **硬性（MUST）**：本 skill 不可妥协的底线。见下节"硬性规范"。
- **惯例（跟随现有库）**：现有库的命名风格、类型选择、分区习惯。同一模式在库内出现 ≥3 处且无冲突视为强惯例，新表优先跟随；强惯例与外部模板冲突时，跟随惯例并在说明中记录偏离。
- **待确认（问用户）**：单位口径、复权方式、时区、PIT 语义、新旧规范冲突、执行权限。未确认前不写进 DDL 和契约。

## 硬性规范

1. **探索只读。** 只用只读账号与只读语句；探索阶段禁止 DDL/DML。
2. **预算先行。** 探索查询声明行数、扫描量与时间上限；禁止无界 `SELECT *` 与全库 `SHOW CREATE TABLE` 式扫描。
3. **默认不执行。** DDL 默认作为脚本交付；执行写操作必须有用户明确要求 + 有写权限的专用账号，破坏性变更（删列、改类型、重建）需单独确认。
4. **注释必写。** 每张表与每个业务列必须有注释；列注释写明口径、单位、来源；示例值用脱敏值。
5. **精确数值。** 金额、价格、数量、净值用 `DECIMAL` 或引擎等价精确类型，禁止 `FLOAT`/`DOUBLE` 存金额与价格。
6. **时间语义显式。** 区分事件时间、可得时间、摄取时间；时区显式声明；交易日用 `DATE`，事件时间用带时区时间戳。
7. **主键必声明。** 每张表声明主键或唯一键；复合键的列序等于筛选粒度顺序。
8. **证据分级。** 探索观察标 `OBSERVED`，语义推断标 `INFERRED`，只有用户确认或带版本规范支持的才标 `CONFIRMED` 并写进契约。

## 执行流程

1. **确认边界。** 记录用途、市场、标的类型、实体范围、时间范围、引擎、交付物（DDL/设计说明/契约），以及是否允许执行写操作。
2. **认引擎。** 判定存储引擎与方言（MySQL、PostgreSQL、ClickHouse、Doris、StarRocks、MaxCompute、DolphinDB 等），据此决定元数据查询语法与 DDL 方言。这一步必须在第一条探索查询之前完成。
3. **探索惯例。** 读元数据：表清单、列、类型、可空性、默认值、注释、主键/唯一键、索引、分区、现有 DDL；分层采样看少量真实行确认口径。见 `references/exploration.md`。
4. **对照规范。** 按需读命名、类型约束、分区三份参考，把探索结果归入"硬性/惯例/待确认"三层。
5. **取投研范式。** 按上面的场景表读 `references/investment-research.md` 对应小节，取主键、时态、单位、复权口径建议，不照抄示例字段名。
6. **设计裁决。** 惯例与规范冲突时按优先级：用户明确要求 > 库内强惯例（≥3 处一致）> 外部规范；每次偏离都记录理由与影响。
7. **写 DDL。** 按方言生成：表注释、列注释、约束、分区、索引、兼容迁移（`ADD COLUMN` 优先）。见 `references/partitioning.md`。
8. **交付。** 产出 `conventions.md`、DDL、`design.md`、`contract.yaml` 四件套；自检硬性规范是否全部满足。

正反例见 `examples/few-shots.md`。

## 交付物要求

- **惯例清单** `conventions.md`：逐条惯例的观察、证据等级（OBSERVED/INFERRED）、依据、反证条件；强惯例标注出现次数。
- **DDL** `.sql`：按引擎原生方言，含表注释与逐列注释、主键/唯一键、CHECK 与默认值、分区与索引；迁移类变更给出向后兼容写法；文件名带版本号（如 `0001_create_dwd_market_daily_bar.sql`）。
- **设计说明** `design.md`：每张表的目的与消费者、主键设计理由、时态列职责、单位与币种、时区、复权口径、PIT 语义、与现有表的引用关系、待确认清单。
- **数据契约** `contract.yaml`：与 `finance-data-qc/references/deliverables.md` 的 `contract.yaml` 同构，并新增 `schema` 字段描述列定义。只写 `CONFIRMED` 语义，未确认的写 `null` 并列入待确认清单。见 `references/data-contract.md`。

## 必须停下的情况

- 连接信息里有明文口令、私钥或会被写进交付物的令牌。
- 只有写权限账号可用，无法建立只读探索边界。
- 任务要求直接在生产库执行破坏性 DDL（删除、改类型、重建），且未获用户对具体语句的明确批准。
- 探索查询无法限定投影、实体、时间、分区或结果上限，可能形成无界扫描。
- 引擎方言未知却要求产出可执行 DDL；先确认引擎再继续。
- 探索样本会暴露未脱敏的账户、持仓、交易或客户信息。
- 需求实质是质检、管道、查询接口、治理或合规的最终结论：保存探索观察，回到 `using-data-dev` 选对应责任。
