# 金融投研数据质检

服务券商与基金的分析师、研究员和给他们供数的人。默认假设：**上游没有质量监控，字段注释不可信，测试库与生产库不一致**。你的任务不是相信数据，而是用最少的查询找出会让研究结论出错的地方。

任务按**两阶段**推进：

- **阶段一 · 探索与试探性检测**：摸清每张表有哪些出错方式（覆盖全、不重叠）。对应"**发现并定级**"子流程：边界 → 引擎 → 探索 → 场景/横切 → 筛缺陷 → 执行反证 → 定级。
- **阶段二 · 甄别固化与策略设计**：把阶段一的发现**甄别**成两类——值得固化为常驻监测的、只进报告的，并给固化的检查做运行策略。对应"**固化与设计**"子流程：过甄别门 → 落固化基准 → 定运行策略 → 交付。
- **条件触发**：阶段二**不一定执行**——只有当阶段一有"高复发 × 高静默成本 × 成本可承受"的发现时才进入；没有值得固化的发现就直接交付报告，跳过阶段二。

质量控制停止在"发现"，只有少数值得的发现进入"持续监测"。

## 这个 skill 交付什么

用户会指定一批表，让你产出两样东西：

1. **数据质量审查报告**（`report.md` + `evidence.json`）：逐项缺陷的观察、证据等级、PASS/BLOCK/WATCH 裁决、影响面与待补证据。
2. **监测脚本 / SQL**（`checks/`）：把本次发现的缺陷固化成可定时重跑的检查，交给用户落地为常驻监控（对应第 10 类缺陷“监控缺失”）。

审查报告是一次性结论，监测脚本是可复用资产。两者都必须真实可重跑，不能是自然语言描述。

## 十类缺陷：逐类判适用性

对每张表把这十类走一遍，但**只执行"适用且有判定前提"的检查**。逐类标记：`执行` / `不适用` / `前提不足暂挂`。不要对所有表机械跑满十类。检测手法、反证路径、"何时不能下结论"见 `references/defect-catalog.md`。

**互斥归属纪律（MECE 的 ME 半边）：** 每条观察只归属一个 `check_id`，不允许双报。双报现场（如单位错配既像"命名与单位"又像"数值错误"）按主责任单一归属，另一类在备注写"由 X 类捕获"，不重复列条目。理由：保证报告无重复条目、每项结论可追溯单一检查。

| 缺陷族 | 一句话 | 先看什么 |
|---|---|---|
| 主键重复 | 业务主键出现多行，其中一行信息残缺 | 声明主键的 count vs distinct，重复组内字段差异 |
| 缺失 | 原始表有值但下游字段空，或整类口径没建 | 分实体、分日期、分字段的空值率，与上游对照 |
| 连续性 | 序列断档，看起来"有数据"但月均只有几条 | 按实体×日历的记录数分布，最小/最大间隔 |
| 数值错误 | 量级离谱、单位错、符号错、跨字段矛盾 | 极值、量级分位、跨字段可复算关系 |
| 时效 | 应到未到，或到得比承诺晚 | 最后更新时间、到达延迟分布、批次节奏 |
| 命名与单位 | 同义字段跨表不同名、不同单位、不同时区 | 同义字段清单，量级比对，时区抽样 |
| 注释口径 | 注释能被读成两种意思，或与实际计算不符 | 注释措辞歧义，用数据反推真实口径 |
| 维度污染 | 分类字段混入其他体系的标签，一统计就翻倍 | 枚举值取值域，分组求和与总量对账 |
| 接口层 | 传参 20 返 少、失效标的被捞出、查询超时 | 请求数与返回数对账，边界与分页，慢查询 |
| 监控缺失 | 上述缺陷没有常驻校验，靠人肉发现 | 有没有落地的持续校验与告警 |

## 定级只认三种证据

- **查到的（OBSERVED）**：查询、文件、元数据实际返回什么。
- **推断的（INFERRED）**：字段含义、异常原因、规则是否适用的假设。
- **确认的（CONFIRMED）**：带版本的规范或数据契约、用户对该范围的明确确认、用独立数据源或业务关系复算成功。

定级规则：

- 只有 `CONFIRMED` 口径才能给 `PASS` 或 `BLOCK`，且必须能追溯到可重跑的检查和同一数据范围。
- 只凭字段名、注释或数值分布得出的结论只能给 `WATCH`，不得直接判 `BLOCK`。
- 检查没跑、跑不完或预算不够，写明停止原因。**不要把"没发现问题"写成 PASS。**

## 开工前先落四件事

1. **只读。** 只用只读账号和只读语句。禁止 DDL/DML，禁止无界 `SELECT *`。
2. **范围。** 记下用户指定的表清单、市场、标的类型、实体集合、时间范围、频率、这批数据要拿去做什么（选股、回测、估值、报告取数）。
3. **查询预算。** 先声明行数、扫描量、执行时间或 API 次数上限，再发第一条查询。每轮查询写明目的、投影列、过滤条件、上限。
4. **未知就写未知。** 不清楚的口径列进未知清单，不要用字段名猜、不要拿其他市场的阈值套。

## 执行流程

执行遵循两个阶段的子流程：阶段一必走（发现并定级）；阶段二**条件触发**（有值得固化的发现才进入，否则直接交付报告）。

### 阶段一：探索与试探性检测（发现并定级）

1. **确认边界。** 逐表登记用途、市场、标的类型、实体范围、时间范围，以及用户要的交付物（报告、监测脚本或两者）。
2. **认引擎。** 先判定每张表的存储引擎（关系库、数仓、ES、Mongo、时序库、向量库、文件、API），据此定只读方式、分页、采样与成本估算。见 `references/engine-adapters.md`。这一步必须在第一条业务查询之前完成。
3. **摸结构、估代价。** 读元数据：字段类型、分区、索引、声明约束、行数量级；用执行计划或引擎等价能力确认不会扫全表。见 `references/exploration.md`。
4. **漏斗式采样统计。** 按"元数据 → 小范围侦察 → 分层统计 → 异常下钻 → 有理由地扩大"推进。`LIMIT` 不等于限制扫描；不得一上来跑全历史 `COUNT DISTINCT`、高基数 `GROUP BY` 或大表 join。见 `references/sampling-statistics.md`。
5. **选参考（场景/横切）。** 按表的内容加载对应场景参考，按触发条件加载横切参考（跨表、时效、事故库），取判定前提，不照抄阈值。
6. **筛缺陷。** 对十类逐类判适用性，只保留适用且有前提的检查；每条观察单一归属一个 check_id。见 `references/defect-catalog.md`。
7. **执行反证与定级。** 优先用能形成闭环的关系复算（价格×数量、分组求和对总量、分钟重算日频、上游原始表对下游宽表），而不是继续堆分布统计；逐项给证据等级与 PASS/BLOCK/WATCH，写清影响面与待补证据。

阶段一产出**审查报告与全部发现的定级**（一次性结论）。

### 阶段二：甄别固化与策略设计（条件触发）

**进入条件：** 阶段一存在"高复发 × 高静默成本 × 成本可承受"的发现；没有则跳过本阶段，直接交付报告。

8. **过甄别门。** 对每个发现问三问：复发风险？静默失败成本？检测成本？一次性事故只进报告不固化；周期复发 × 高静默 × 可承受优先固化；成本不成比例的优化（降频/降采样）或放弃。
9. **落固化基准。** 能对照 `contract.semantics.formula` 复算核验且高复发的检查优先固化为 `checks/`；无复算依据的标注"需先补契约"并写进设计说明，不静默固化。
10. **定运行策略。** 为每个固化检查定 schedule（跟随 `references/freshness.md` 四种制度）、threshold、alert_on、depends_on。
11. **交付。** 产出过甄别门的 checks/ 与运行策略，随报告按运行版本化保存，历史运行不许覆盖。见下节与 `references/deliverables.md`。

正反例见 `examples/few-shots.md`。

## 交付物要求

- **审查报告** `report.md`：数据范围与快照、查询预算与实际消耗、逐项 `check_id` 的观察/证据等级/裁决、`INFERRED` 假设的依据与反证条件、时效与覆盖观察、与上次运行的差异；每条观察单一归属一个 `check_id`。
- **机器可读证据** `evidence.json`：每条检查的可重跑文件引用、参数、观察结果、证据等级、裁决。
- **监测脚本 / SQL** `checks/`：**只含过甄别门的检查**（阶段二产出）——高复发 × 高静默成本 × 成本可承受；能对照 `contract.semantics.formula` 复算核验的优先。每条固化为该引擎原生可执行格式（SQL 用 `.sql`，ES/Mongo/时序/向量用其原生请求，Python 用 `.py`），带稳定 `check_id`、参数化数据范围、判据与告警阈值建议，供用户直接接入调度。不得把非 SQL 检查伪装成 `.sql`。
- **运行策略**（随 checks/）：每个固化检查的 `schedule`（跟随 `freshness.md` 四种更新制度，未确认写 `null`）、`threshold`、`alert_on`（告警路由/级别/连续失败次数）、`depends_on`（数据就绪依赖）。
- 监测脚本要能独立于本次会话运行：参数化时间窗与实体范围，不硬编码一次性快照。一次性事故、低频可承受、成本不成比例的发现**只进报告，不固化**。

## 必须停下的情况

- 连接信息里有明文口令、私钥或会被写进报告的令牌。
- 只能拿到有写权限的账号，或任务要求执行 DDL/DML。
- 查询无法限定投影、实体、时间、分区或结果上限，可能形成无界扫描。
- 已用或预估扫描量超出批准的查询预算。
- 样本会暴露未脱敏的账户、持仓、交易或客户信息。
- 数据是压缩、加密、专有二进制或流式形态，没有安全的只读解析方式。
- 任务实质是要 DDL 设计、管道编排、查询接口设计、治理或合规的最终结论：先保存已有观察，再回到 `using-data-dev` 选对应责任。
