# 场景前提：公告、研报与事件

覆盖交易所公告、招股与定期报告文本、研报、以及从文本抽取出的结构化事件。这里只给**判定前提**，检测手法回 `defect-catalog.md`。

这类数据的特点是**事件驱动 + 多段链路**，所以缺陷集中在时效和抽取质量两头。

## 链路分段是第一步

公告或研报从发布到可用要走：发布 → 采集 → 解析 → 抽取 → 落库 → 对外可见。质检必须能定位到段：

- 逐段记录时间戳，算各段耗时，找瓶颈。
- 确认解析任务是轮询还是事件触发；轮询间隔构成延迟下限。
- 确认推送是逐条还是整批完成后统一推送。批量推送时批内最后一条的延迟等于整批耗时，详见 `freshness.md`。
- 解析失败的样本去了哪里：有没有失败队列、失败率是否可见。静默丢弃是最危险的形态，因为下游看到的是"没有这条公告"。

## 专属检查

- **应到未到**：按发布日历与实体范围构造应有公告集合，与库内比对。用官方披露渠道核对，不要用库内自身数量做基准。
- **去重与版本**：同一公告的更正版、补充版、多渠道重复。要确认业务主键包含哪些维度（公告编号、发布时间、版本），否则更正版会与原版并存且下游随机取一条。
- **实体绑定**：公告绑定到哪些标的，一份公告涉及多个主体时如何落地。绑定缺失会让事件在筛选中消失；绑定过宽会污染统计。
- **事件抽取正确性**：抽取字段（事件类型、金额、比例、日期、方向）能否与原文对齐。抽样人工复核，并保留原文定位（页、段、字段来源），否则错误不可追溯。
- **事件类型取值域**：事件类型枚举里有没有混入其他体系的标签，见 `defect-catalog.md` 第 8 类维度污染。
- **事件后一致性**：事件应当引起的后续变化是否发生。分红送转应对应复权因子与价格跳变，重大资产变动应对应主数据或财务变化。对不上时定位是事件错、行情错，还是两者时点不同。
- **点时可见**：事件的可得时间必须落库。研究要问"当时能不能看到这条公告"，只有事件发生日不足以回答。

## 定级红线

- 抽取正确性只能靠与原文比对来确认；抽取字段之间自洽不构成 CONFIRMED。
- 没有权威披露清单时，"漏了公告"只能 WATCH。
- 事件后一致性对不上时，先排除时点与复权口径差异，再判某一侧错误。
- 文本样本可能含敏感或未公开内容，抽样时按 STOP 条件处理，不要把原文大段写进报告。
