# 时效与覆盖

先确认这批数据属于哪种更新制度，再谈延迟。把不同制度套同一个阈值，是时效判断出错的主因。

## 四种更新制度

| 制度 | 典型对象 | 该看什么 | 不该做什么 |
|---|---|---|---|
| 实时/盘中延迟 | 逐笔与快照行情、实时指标 | 交易时段内的到达延迟分布、时段外是否应停更 | 不要用非交易时段的"不更新"判为滞后 |
| T+1 定点 | 部分日频衍生字段、融资融券类余额、基金净值 | 约定时点前后的到达情况、当期上游是否有值 | 不要在约定时点之前判缺失 |
| 披露驱动 | 公告、财报、研报 | 披露发生到库内可见的时延、链路各段耗时 | 不要用固定日频节奏衡量事件驱动数据 |
| 定期发布 | 宏观与行业指标 | 官方发布日历、修订版本的到达 | 不要把未到发布日的空缺当缺失 |

制度未确认时，延迟只能标 `OBSERVED`/`INFERRED`，不能直接 `BLOCK`。

## 应到未到

完整性用"应有集合"来判，不要用总行数。

1. 先构造应有集合：交易日历（或发布日历）× 实体生命周期（上市、退市、停牌、基金成立与清算）。
2. 与实际数据左连接，取缺口。
3. 逐个缺口找解释：休市、半日市、停牌、尚未上市、供应商未覆盖、当期上游无值、本层同步失败。
4. 解释不掉的缺口才是缺陷；覆盖起点或采购范围未知时只能 `WATCH`。

同时看**覆盖起点**：首个有效观测在哪一天，是否满足消费方要求的历史长度。回测场景对历史长度的要求比取数场景严得多。

## 链路分段

"数据慢"要定位到具体一段。把能拿到的时间戳排成链：业务发生时间 → 上游可得时间 → 采集/摄取时间 → 加工完成时间 → 对外可见时间。逐段算耗时，找出瓶颈段。

两个高频瓶颈：

- **扫描间隔过长**：离线任务按固定间隔轮询，间隔本身就构成下限延迟。
- **批量推送**：整批处理完才统一推送，而不是成功一条推一条。此时批内最后一条的延迟等于整批耗时，前面已就绪的记录被白等。检测方式：比对同一批次内最早与最晚记录的可见时间，若几乎相同而业务时间跨度很大，就是批量推送。

## 修订与回补

- 上游回补历史或修订数值时，要能看到版本或更新时间；只有当前最终态时，不能声称历史从未被改过。
- 修订会让"昨天核对过的数字今天变了"，验收结论必须绑定数据范围与快照时点。
- 点时消费（回测、估值）必须用"可得时间 ≤ 截止时间"筛版本，不能用当前最终态替代当时可见态。
