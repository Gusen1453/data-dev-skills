# 十类缺陷的检测手法

每类给四件事：怎么查、如何反证、何时不能下结论、常见根因。SQL 只是思路示意，按 `engine-adapters.md` 换成用户实际引擎的语法，并且都要带范围过滤和结果上限。

判定纪律贯穿全表：字段名、注释、单一分布都只是线索，只能给 `WATCH`；要给 `PASS` 或 `BLOCK`，必须有带版本的口径、用户确认，或用独立来源复算成功。

---

## 1. 主键重复

**怎么查**

- 对声明主键和候选业务主键分别比 `count(*)` 与 `count(distinct 键)`；差值就是重复量。
- 抽几组重复行做整行对比，看差异集中在哪些列。
- 检查"同一实体同一天应只有一行"这类业务级唯一性，而不只是表上有没有主键约束。

```sql
select 实体键, 日期键, count(*) c
from 表
where 日期键 between :开始 and :结束
group by 1, 2 having count(*) > 1
limit 200
```

**如何反证**

- 重复组内如果一行字段齐全、另一行交易所/上市状态等为空或为"未知"，这不是正常多版本，是脏写入或多源合并没去重。
- 如果差异集中在版本列、快照时间、口径视图类型或币种列，那可能是**维度没固定**造成的合理多行：确认消费方是否必须固定这些维度取一行。
- 用上游原始表的键基数对照，判断重复是上游带来的还是本层加工产生的。

**何时不能下结论**

- 主键未确认前不能说重复：先问清业务主键是"实体+日期"还是"实体+日期+口径+币种"。
- 表设计上允许多版本（拉链表、快照表）时，重复行数本身不是缺陷，要看消费方有没有正确取一行。

**常见根因**：多源合并未去重；口径视图类型、币种等维度未固定；补数任务重跑未幂等；实时与日终数据写进同一张表。

## 2. 缺失

分三层看，别混为一谈：**整类口径没建**、**字段没同步过来**、**个别实体某天为空**。

**怎么查**

- 字段级：按时间窗统计每列空值率，再按市场、标的类型分组拆开看。
- 记录级：用日历 × 实体生命周期算出"应有"集合，与实际做左连接找缺口。
- 口径级：核对承诺提供的指标清单与实际有值的指标清单，统计"有列但全空"的字段数。

```sql
select 市场, count(*) 总数,
       sum(case when 目标字段 is null then 1 else 0 end) 空值数
from 表 where 日期键 between :开始 and :结束
group by 1
```

**如何反证**

- 拿上游原始表同一实体同一期的值比对：上游有值而下游空，是同步或映射漏了列；上游也空，是采购或供应商覆盖问题。
- 同一实体前几天有值、这天为空，通常是当期更新失败或供应商当期未提供，不是字段设计问题——查更新时间与批次日志。
- "有列但全空"要确认该口径是否真的采购了，例如某些市场只有累计口径、没有 TTM，就不是 bug 而是覆盖缺口，需要在契约上写明。

**何时不能下结论**

- 停牌、未上市、已退市、基金成立前的空值是正常的，先叠加生命周期再判断。
- 覆盖起点和采购范围未知时，历史空洞只能 `WATCH`。

**常见根因**：宽表映射漏列；供应商当期未提供而任务不告警；某市场压根没采购该口径；日内表未建但接口已开放。

## 3. 连续性

**怎么查**

- 按实体统计每月/每周记录数分布，看有没有"月均个位数"这种明显不对的量。
- 算相邻记录的时间间隔，取最大间隔和间隔分布。
- 生产与测试、日频与分钟频分别统计，别只在一个环境验。

```sql
select 实体键, date_trunc('month', 日期键) m, count(*) c
from 表 where 日期键 between :开始 and :结束
group by 1, 2 order by c asc limit 200
```

**如何反证**

- 用交易场所官方日历重算应有交易日数；能被休市、半日市、停牌解释的缺口不算缺陷。
- 缺口是否只出现在某一市场、某一来源、某一时间段？只在生产环境断档而测试环境正常，通常是调度或写入链路问题，不是数据源问题。
- 指数、基金这类非逐日披露的对象，先确认披露频率再判断。

**何时不能下结论**

- 没有确认市场、时区、会话定义或日历版本时，缺口只能 `WATCH`。
- 只凭首次/末次出现日期不能判定生命周期错误。

**常见根因**：调度只在部分日期成功；写入按分区覆盖但分区键算错；多市场共用一个日历；上线时只回补了少量样本。

## 4. 数值错误

**怎么查**

- 极值与量级：看最大最小值、分位数、数量级分布。市值、成交额这类字段的量级错误一眼能看出来。
- 跨字段可复算关系：价格与数量对金额、单季相加对累计、成分加权对指数点位、分项相加对合计。
- 符号与取值域：应为非负的字段有没有负数，比率字段是否落在制度允许区间。

**如何反证**

- 拿独立来源或另一张表复算同一事实。量级差 100 倍、差 10000 倍通常是单位（元/万元/百万、小数/百分比）或币种换算错误，而不是业务异常。
- 跨字段关系不成立时，先排除合约乘数、费用、净额毛额、舍入，再判断是数据错。
- 极端值先查是不是真实事件（除权、重组、极端行情），用公司行动或公告对照。

**何时不能下结论**

- 只有分布证据、没有确认口径时不能 `BLOCK`。例如涨跌幅字段全落在 `[-0.2, 0.2]`，可能是小数口径而非缺失限幅，必须先确认单位。
- 单位、币种、乘数任一未确认时，复算不成立只能 `WATCH`。

**常见根因**：单位混用；币种未换算或未固定；乘数缺失；上游修订未回流；错误值直接进了对外展示口径。

## 5. 时效

判定制度见 `freshness.md`，这里只列检测动作。

**怎么查**

- 查每个数据集的最后更新时间与最新业务日期，两者都要看。
- 算到达延迟分布：业务时点到可见时点的差，分交易时段内外、分市场看。
- 看批次节奏：是逐条推送还是整批处理完才推，批次内最早与最晚记录的时间差有多大。

**如何反证**

- 与承诺的更新制度对照：实时、盘中延迟、T+1 定点、披露后同步，各自阈值完全不同，不能混用。
- "应到未到"要先确认该业务日是否真的应该有数据，再确认是上游没给还是本层没同步。
- 延迟集中在链路某一段时，用各段的时间戳定位，而不是笼统说"数据慢"。

**何时不能下结论**

- 没有确认更新制度或 SLA 时，延迟只能 `OBSERVED`/`INFERRED`，不能直接 `BLOCK`。

**常见根因**：离线任务扫描间隔过长；整批处理完才统一推送而不是成功一条推一条；上游定点更新而下游按更早时点消费；跨时区的"当天"理解不一致。

## 6. 命名与单位

跨表统一的完整清单见 `cross-table-consistency.md`。

**怎么查**

- 列出同义字段在各表的名称、类型、单位、时区，做一张对照表。
- 同义字段抽同一实体同一时点的值做量级比对，量级不一致就是单位不一致。
- 时区：拿一个已知时点的记录，看两张表的时间戳是否相差固定小时数。
- 库表名：比对测试库与生产库的库名、表名、字段名，前缀与命名规范是否一致。

**如何反证**

- 单位差异要用能复算的关系确认，而不是只看小数位。
- 时区差异确认到底是存储时区不同，还是同一时区但业务日归属规则不同。

**何时不能下结论**

- 仅从量级或小数位推断单位时不能给 `PASS`/`BLOCK`，需要契约或用户确认。

**常见根因**：不同表由不同人不同时期建；跨市场数据源报价惯例不同；测试库建表脚本与生产不同；重要字段（如币种）只在部分表里有。

## 7. 注释口径

**怎么查**

- 逐条读关键字段注释，标出能被读成两种意思的表述（分子分母能互换的比率、"总"与"主营"混用、期间口径没写清是单季还是累计）。
- 用数据反推真实口径：按注释理解算一遍，与字段实际值比对。
- 同一指标在不同市场的表里注释是否一致，有没有只改了一边。

**如何反证**

- 用可复算关系确定真实口径（例如用两个基础字段相除还原比率方向），再判断注释是否与实际一致。
- 找权威指标定义或数据契约比对措辞。

**何时不能下结论**

- 只觉得注释"读起来别扭"但数据与两种理解都不矛盾时，记 `WATCH` 并申请权威口径，不要自行改写语义。

**常见根因**：注释从供应商文档直译；比率类字段分子分母表述省略；多市场分批治理只改了一边；字段含义随需求变化但注释没跟。

## 8. 维度污染

分类维度里混进了另一套分类体系的取值，一做分组统计就多出条目或总量翻倍。

**怎么查**

- 对行业、板块、题材、市场类型、交易所、状态等分类字段取全部枚举值和各值计数，人工过一遍取值域。
- 分组求和与总量对账：按该维度分组后的实体数或金额之和是否等于总量。
- 检查一个实体在该维度上是否被打了多个标签。

```sql
select 分类字段, count(*) c, count(distinct 实体键) e
from 表 where 日期键 = :某日 group by 1 order by c desc
```

**如何反证**

- 拿该分类体系的官方标准取值表比对，找出不属于该体系的值。
- 确认设计意图是"单标签"还是"多标签"：多标签下总量不守恒是正常的，但消费方必须知道不能直接求和。

**何时不能下结论**

- 分类体系版本与是否允许多标签未确认时，只能 `WATCH`。

**常见根因**：一个字段同时存放两套分类标准的标签；同一实体多标签但下游按单标签统计；分类体系换版后新旧值共存。

## 9. 接口层

数据本身对，但通过查询接口拿出来就不对。

**怎么查**

- 请求与返回对账：传入 N 个实体，返回是否覆盖 N 个；有没有静默截断、默认分页上限、隐式 limit。
- 边界用例：单个实体、上限个实体、超上限、空集、不存在的实体、跨市场混合请求。
- 过滤条件是否真的生效：改日期范围后，本应被排除的失效标的还在不在结果里。
- 慢查询：记录执行时间与扫描量，定位是缺索引、扫全表还是过滤下推失效。

**如何反证**

- 用直连查询同一范围的结果与接口返回逐条对齐，差集就是接口层引入的问题。
- 截断要区分是接口上限、序列化限制，还是下游展示层截断。

**何时不能下结论**

- 未确认接口的分页与上限约定时，返回数少不能直接判为 bug，先取约定。

**常见根因**：默认分页上限未透传；批量入参上限未校验也未报错；过滤条件与业务有效期脱钩，已失效标的仍被捞出并参与计算；缺少针对查询范围的索引。

## 10. 监控缺失

前九类问题只要没有常驻校验，就一定会重复发生。验收时把"有没有监控"本身当成一条检查。

**怎么查**

- 问清现有校验有哪些、跑在哪一层、失败会不会告警、告警给谁。
- 核对本次发现的每类缺陷，是否有对应的常驻校验能自动发现。
- 检查最基础的三条是否存在：主键唯一性、关键字段非空、更新时效。

**如何反证**

- 让上游展示最近一次校验失败的记录与处理结果。有校验但从不失败、或失败无人处理，等于没有。

**何时不能下结论**

- 监控体系归属不在本次范围时，记为 `WATCH` 并写进报告的遗留风险，不要替对方设计监控体系。

**常见根因**：只在需求上线时人工验一次；校验写在临时脚本里没落地；发现问题依赖使用方投诉。
