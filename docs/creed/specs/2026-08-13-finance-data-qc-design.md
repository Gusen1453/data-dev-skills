# 金融投研数据质量验收规格

**状态：** Approved  
**日期：** 2026-08-13  
**修订：** 2026-08-13（投研场景校准）、2026-08-13（合并为单执行器，按通用缺陷族组织）  
**Owner：** 仓库维护者

## 1. 一句话说明

让服务券商/基金买方卖方分析师、研究员的数据开发人员，在多市场、多类型投研研究库上完成可信验收：按十类通用缺陷族逐项排查，用可证伪推断和版本化证据得出结论，一次验收同时覆盖内容正确性、跨表一致性与时效覆盖，而不是用大而浅的清单制造虚假安全感。

## 2. 用户场景

### 场景 A：质检请求被路由到唯一执行器

- **谁：** 服务投研分析师的数据开发人员。
- **何时：** 用户描述行情、财报、公告、主数据、基金、宏观行业数据的验收或排障需求。
- **操作：** 总入口识别为质量验收后，直接进入 `finance-data-qc` 执行，不再往下分层路由。
- **看到：** Agent 先要只读连接、数据范围与查询预算，再开始探索。

### 场景 B：面对陌生 schema 主动探索

- **谁：** 接入新供应商或历史投研库的数据开发人员。
- **何时：** 字段口径、市场、标的类型、更新频率或时态语义不完整。
- **操作：** 在只读与预算内先读元数据，再按市场、标的类型、时间、实体、状态分层采样。
- **看到：** 观察事实、候选语义、依据、反证条件；不照抄 few-shot 阈值。

### 场景 C：启发式推断不能伪装成事实

- **谁：** 检查命名、注释、数值分布与更新时效的数据开发人员。
- **何时：** 看起来异常但缺少权威口径、契约或独立复算关系。
- **操作：** 查询结果标 `OBSERVED`，语义与原因判断标 `INFERRED`，继续找复算关系或权威口径。
- **看到：** 只能 `WATCH`，不能直接 PASS/BLOCK。

### 场景 D：证据闭环后形成验收结论

- **谁：** 需要签署质量结论的数据开发人员。
- **何时：** 已有带版本的规范、数据契约、用户确认，或独立复算成功。
- **操作：** 升级为 `CONFIRMED`，执行可重跑检查，记录适用前提、数据范围、规则版本与结果。
- **看到：** PASS/BLOCK 可追溯，他人可重跑并解释差异。

### 场景 E：按通用缺陷族排查

- **谁：** 验收任意投研数据集的开发人员。
- **操作：** 逐类判断适用性：主键重复、缺失、连续性、数值错误、时效、命名与单位、注释口径、维度污染、接口层、监控缺失。
- **看到：** 同一套缺陷族适用于行情、财务、公告、宏观；场景差异只体现在判定前提上。

### 场景 F：跨表拼接暴露口径不齐

- **谁：** 需要把行情、财务、主数据、实时表 join 起来供分析师取数的开发人员。
- **何时：** 单表全绿但跨表结果错位、金额不可比、join 静默丢行。
- **操作：** 走跨表一致性核对：单位、命名、市场类型、交易所、币种、标的代码、库表名、时区、实时表与日频表衔接。
- **看到：** 问题定位到具体核对项，而不是在单表内继续找错。

### 场景 G：多市场适配与时效覆盖

- **谁：** 同时维护 A/H/美股、基金、指数、外汇投研库的开发人员。
- **何时：** 同类数据在不同市场有不同日历、时区、披露制度与覆盖起点。
- **操作：** 先用适配表确认判定前提，再套用同一缺陷族；按四种更新制度分别衡量时效。
- **看到：** 未知市场前提时不套用其他市场阈值。

### 场景 H：高风险条件下安全失败

- **谁：** 在生产投研数据源上执行质检的开发人员。
- **何时：** 明文凭据、非只读、无界查询、预算超限、敏感样本或不支持的数据形态。
- **操作：** STOP 或降级，并记录原因。
- **看到：** 不泄露凭据、不写库、不把"未执行"写成 PASS。

### 场景 I：发现其他工程责任的问题

- **谁：** 在质检中发现 DDL、管道、查询接口、治理或合规问题的开发人员。
- **操作：** 保存观察证据，建议回到 `using-data-dev` 走对应责任。
- **看到：** 质检不越权给出这些领域的最终结论。

## 3. 范围

**包含：**

- 数据开发总入口 `using-data-dev` 按工程责任路由，只展示真实可用能力。
- 唯一质检执行器 `finance-data-qc`，`SKILL.md` 承载十类通用缺陷族、三级证据与执行流程。
- 统一参考：`defect-catalog.md`（检测手法）、`cross-table-consistency.md`（跨表统一）、`freshness.md`（时效与覆盖）、`real-world-cases.md`（脱敏真实事故库）、`exploration.md`、`engine-adapters.md`、`deliverables.md`。
- 场景专属参考四份：市场与主数据、财务与估值、公告与事件、宏观与行业，只写判定前提与专属检查。
- 一份 few-shot：含证据闭环正例、只能停在 `INFERRED/WATCH` 的反例、降级与 STOP 例。
- 中文操作规程为主，保留必要技术标识。

**不包含：**

- 按场景拆多个 skill — 原因：缺陷族高度重复，跨表问题无处归属。
- 组合持仓与净值运营验收、订单成交清算账本验收 — 原因：属交易运营域，不在投研研究库。
- 数据契约与 DDL 设计、管道开发、查询接口设计、治理、合规审查 — 原因：各有独立最终产物与结论权限。
- 按字段或按市场穷举全部规则 — 原因：压制泛化并造成规则漂移。
- 以数据库引擎作为一级分类 — 原因：技术栈只是适配维度。
- 未脱敏的内部库表名、字段名与人名进入仓库 — 原因：公开仓库。

## 4. 决策记录

| 决策 | 选择 | 放弃 | 原因 |
|------|------|------|------|
| 主用户与主战场 | 投研研究库 | 交易运营库并行 | 对齐券商/基金买卖方分析师日常数据 |
| 执行器数量 | 单执行器 + 场景参考 | 按市场参考/基本面/披露/宏观拆四个 skill | 缺陷族通用，拆开会重复抄规则，且跨表问题无归属 |
| 规则组织方式 | 按通用缺陷族组织正文，场景差异下沉到 references | 按场景组织正文 | 用户实际遇到的问题按缺陷族分布，不按场景分布 |
| 案例来源 | 团队真实事故库，脱敏后入库 | 只写抽象原则 | 抽象原则读不出可执行动作 |
| 脱敏边界 | 去人名、去内部库表字段名，保留技术现象 | 原样收录 | 公开仓库不得泄露内部 schema 与人员信息 |
| 多市场落地 | 适配表给判定前提 | 按市场拆 skill 或只做 A 股 | 统一方法，保留制度差异 |
| 时效归属 | 统一一份 `freshness.md`，按四种更新制度分档 | 每场景各写一份，或只记 INFO | 制度差异是判定前提，不是场景私有规则 |
| 跨表一致性归属 | 统一一份 `cross-table-consistency.md` | 分散到各场景 | 跨表问题天然横切，分散即丢失 |
| 启发式结论权限 | 推断只能 WATCH，闭环后才能 PASS/BLOCK | 高置信直接 BLOCK | 防止伪确定性 |
| 约束模型 | 高风险硬约束，分析方法自适应 | 全流程硬编码或只写原则 | 约束最差工程师同时保留探索 |
| 总体架构 | 一级路由 + 单执行器 | 两级路由 + 多执行器 | 稳定触发，安全门槛不重复维护 |

## 5. 验收标准

- [ ] 仓库只暴露 `using-data-dev` 与 `finance-data-qc` 两个 skill；README 不再引用任何已下线入口。
- [ ] 十类缺陷族在 `defect-catalog.md` 中都有检测手法、反证路径与"何时不能下结论"。
- [ ] 跨表一致性参考覆盖单位、命名、市场类型、交易所、币种、标的代码、库表名与时区。
- [ ] 时效参考区分实时、T+1 定点、披露驱动、定期发布四种制度，并给出应到未到与链路分段方法。
- [ ] 真实事故库已脱敏：不含人名、不含内部库表与字段名，且每条给出检查思路。
- [ ] 四份场景参考只写判定前提与专属检查，不重复通用规则。
- [ ] 陌生 schema 能在预算内分层探索，并输出可证伪假设。
- [ ] 仅有命名、注释、单一分布线索时保持 `INFERRED/WATCH`。
- [ ] 权威口径或独立复算闭环后才可 PASS/BLOCK，且能追溯到 `check_id`、规则版本、数据范围与快照。
- [ ] 涨跌幅类字段仅有分布证据时不得直接 BLOCK。
- [ ] 明文凭据、写权限、无界查询、预算超限、敏感样本会 STOP 或降级；未执行不写成 PASS。
- [ ] 正文无 `light profiling`、`sample appropriately`、`reasonable ranges` 等不可验收指令。

## 6. 约束

- 默认只读；写操作与数据修复不属于本套件。
- 查询必须有可见预算和边界。
- 示例与证据不得包含明文凭据、私钥、未脱敏敏感样本或内部 schema 标识。
- `OBSERVED` / `INFERRED` / `CONFIRMED` 与 PASS / BLOCK / WATCH 含义全局一致。
- 适配表只提供适用前提与制度差异，不提供可照抄的万能阈值。
- 技术引擎只改变语法，不改变证据纪律。

## 7. 构建方式概述

`using-data-dev` 按工程责任路由到 `finance-data-qc`。`finance-data-qc` 的 `SKILL.md` 写清安全门槛、十类缺陷族总表、三级证据与六步流程；检测手法、跨表核对、时效制度、真实事故与场景判定前提全部下沉到 `references/`。交付采用稳定契约、可重跑检查与按运行版本化的证据包。

## 8. 开放风险

- 单个 `SKILL.md` 可能随时间膨胀。缓解：正文只留缺陷族总表与流程，新增内容一律进 references。
- 缺陷族与场景参考可能出现重复表述。缓解：场景参考只允许写判定前提与专属检查，通用手法一律引用 `defect-catalog.md`。
- 事故库脱敏后可能失去可操作性。缓解：保留量级、字段角色与检查动作，只去掉标识信息。
- 十类缺陷族可能被当作必答清单机械执行。缓解：每类都要求先判断适用性，并保留"不能下结论"的出口。
