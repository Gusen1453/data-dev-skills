## 0. 现状（explore 事实）

任务重构既有执行器 `finance-data-qc`，先列可引用事实，避免新人重读仓库：

- **锚点（已读）：** `skills/finance-data-qc/SKILL.md`（现为扁平"0–8 验收流程"：边界→引擎→探索→选场景→选横切→筛缺陷→定检查→执行定级→交付；交付物含报告 + `checks/` 监测脚本）、`references/defect-catalog.md`（十类缺陷 + 第 10 类"监控缺失"）、`references/cross-table-consistency.md`、`references/freshness.md`（四种更新制度）、`references/deliverables.md`（`checks/` 节现有 check_id/rule_version/适用条件/判据）、`references/sampling-statistics.md`（五阶段漏斗：元数据→侦察→分层→下钻→扩大）、`examples/few-shots.md`（例 2 已有"该检查应落为常驻校验"口头建议但无甄别标准）。
- **断言核对：**
  - ✓ 「阶段一 MECE 的探针机制已存在」——`sampling-statistics.md` 五阶段漏斗就是"试探性检测"：便宜探针先扫、命中下钻。
  - ✓ 「阶段一 MECE 的互斥纪律缺失」——`defect-catalog.md` 只要求"走一遍十类"，未要求每条观察**单一归属一个 check_id**（单位错配可落"命名与单位"也可落"数值错误"）。
  - ✓ 「阶段二（甄别固化）缺口」——`deliverables.md` 的 `checks/` 目前"固化本次发现的缺陷"，无甄别判据、无 schedule/threshold/alert_on/depends_on。
  - ✓ 「可复算固化基准可接契约」——上轮刚落地 `contract.semantics.formula`（DDL + QC + query 三方同构），可用于"能对照公式复算核验的检查才固化"。
- **冲突点：** 不做新 skill、不建新层；只重构既有执行器的阶段与交付约束。

## 1. 一句话说明

把 `finance-data-qc` 重构为**两阶段为纲、子流程附属**的执行骨架：阶段一按 MECE 制度做探索与试探性检测（覆盖全、不重叠），阶段二把值得的发现**甄别**固化为常驻检查并设计运行策略（何时跑、阈值、告警、依赖）。两阶段符合使用直觉的场景化结构；子流程（探索/采集/定级、甄别/固化/策略）附属于对应阶段——阶段一必走，阶段二**条件触发**（仅当有"高复发 × 高静默成本 × 成本可承受"的发现才进入，否则直接交付报告）。质量控制停止在"发现"，只有少量值得的发现进入"持续监测"。

## 2. 用户场景（source of truth）

### 场景 A：一次验收发现多个问题，只有部分值得管

- **谁：** 验收一批新表的数据开发人员。
- **何时：** 一次验收发现：一个一次性迁移事故（数据已修复）、一个每天都会复发的 T+1 滞后、一个成本极高的大表扫描检查。
- **做什么：** 阶段一全量 MECE 探索定级；阶段二对每个发现过甄别门（复发风险 × 静默成本 × 检测成本）。
- **看到：** 迁移事故只写进报告不固化；T+1 滞后固化成 `checks/` 常驻检查并带 schedule=日频、阈值、告警路由；昂贵大表检查被降频/降采样或明确不固化，说明理由。

### 场景 B：探测命中异常，下钻定级

- **谁：** 面对陌生 schema 的质检人员。
- **何时：** 元数据阶段发现某金额字段量级可疑。
- **做什么：** 按五阶段漏斗：侦察（小范围覆盖边界）→ 分层统计（按市场×币种分组看量级分布）→ 定向下钻（解释异常 + 正常对照组）→ 取证定级。
- **看到：** 探针找到异常层后才有定向下钻，不一开始对全历史全字段跑统计。

### 场景 C：两条检查对同一缺陷双报

- **谁：** 质检人员整理检查结果。
- **何时：** 单位错配既符合"命名与单位"又符合"数值错误"。
- **做什么：** 按互斥归属纪律，一条观察只归一个 check_id，主责任优先；另一类写"由 X 类捕获"。
- **看到：** 报告无重复条目，每项结论可追溯单一 check_id。

### 场景 D：固化的检查真的能被调度器执行

- **谁：** 落地常驻监控的开发人员。
- **何时：** 拿到 `checks/` 里的监测脚本。
- **做什么：** 每个检查带 schedule（跟随 `freshness.md` 四种更新制度）、阈值、告警路由、数据就绪依赖。
- **看到：** 能直接接入调度，不猜测"这个检查该多久跑一次、失败告警给谁"。

### 场景 E：可复算的检查优先固化

- **谁：** 质检人员在阶段二甄别。
- **何时：** 两个检查重复风险与成本相近，一个有契约可复算公式、一个没有。
- **做什么：** 按"固化基准 = 可复算"优先固化能对照 `contract.semantics.formula` 复算核验的检查；无复算依据的只进报告或标注为需补契约。
- **看到：** 常驻检查的判据可追溯到契约公式，告警能被独立复算验证。

### 场景 F：监控缺失的反面——什么都固化

- **谁：** 维护者的长期视角。
- **何时：** 持续一年后 `checks/` 膨胀成僵尸清单，多数检查从不告警也没有人看。
- **做什么：** 阶段二的甄别门（防膨胀）拦截"一次性事故/低频可承受/成本不成比例"的固化；每个固化的检查都要过三问。
- **看到：** `checks/` 只含高复发 × 高静默成本 × 成本可承受的检查，维护量有限且都被消费。

### 场景 G：更新制度与调度错配（伪监测）

- **谁：** 质检人员设计监测。
- **何时：** 用户想给披露驱动数据（公告、财报）配"每天 cron"。
- **做什么：** schedule 跟随 `freshness.md` 四种制度：披露驱动看"披露发生到可见的时延"，不按固定日频节奏。
- **看到：** 调度元数据声明制度类型，不套错误节奏；用户知道为什么不能简单日频。

## 3. 范围

**In（本轮）：**

- `finance-data-qc` SKILL.md 流程重构为两阶段骨架：**阶段一 MECE 探索与试探性检测**、**阶段二 甄别固化与策略设计**。
- 阶段一补 **互斥归属纪律**：每条观察单一归属一个 check_id，双报规避（如单位错配主归"命名与单位"，注明"数值错误已捕获"）。
- 阶段二新增 **甄别门（三问）**：复发风险 × 静默成本 × 检测成本；过不去的发现只进报告不固化。
- 阶段二补 **固化基准 = 契约可复算**：优先固化能对照 `contract.semantics.formula` 复算核验且高复发的检查；无复算依据的检查标注"需先补契约"。
- 阶段二补 **策略层**：每个固化检查带 schedule（跟随 `freshness.md` 四种更新制度）、阈值、告警路由、数据就绪依赖；落到 `deliverables.md` 的 `checks/` 结构与 `few-shots.md` 示例。
- `defect-catalog.md` 第 10 类"监控缺失"补"甄别门 = 反伪监控"：不是任何发现都固化。

**Out（本轮）：**

- **检查生命周期（健康/退役）** —— 原因：用户选 A 不含该项；常驻检查的"静默数月"症状与退役路径留待下一轮。
- 新增 skill / 新语义层 / 新台账 —— 原因：包的反膨胀本能；只重构既有执行器。
- 重写场景参考或缺陷族的检测手法 —— 原因：主线仍是十类缺陷与五阶段漏斗，只补归属与甄别。
- 自动执行/部署监测 —— 原因：只产脚本与策略元数据，不代跑生产调度（既有纪律不变）。

## 4. 决策记录

| 决策 | 选择 | 放弃 | 原因 |
|------|------|------|------|
| 流程骨架 | 两阶段（MECE 探索 → 甄别固化） | 扁平 0–8 验收流程 | 区分"发现"与"值得持续监测的发现"，防止所有发现一律固化 |
| 互斥归属 | 每条观察单归属一个 check_id，双报注明互引 | 允许双报/多报 | 报告无重复条目、每结论可追溯，符合 MECE 的 ME 半边 |

| 调度基础 | 跟随 freshness.md 四种更新制度 | 默认日频 | 披露驱动/定期发布数据按日频查是伪监测 |

| 阶段一探针 | 复用 sampling-statistics.md 五阶段漏斗 | 另起炉灶 | 探针机制已存在，只补归属纪律 |

## 6. 约束

- 默认只读；写操作与数据修复不属于本套件。
- `OBSERVED` / `INFERRED` / `CONFIRMED` 与 PASS / WATCH / BLOCK 含义全局一致。
- 不做新 skill、不建新层；只改 `finance-data-qc` 内部阶段与交付约束。
- 技术引擎只改变语法，不改变证据与甄别纪律。
- checks 交付原生可执行格式，不得把非 SQL 伪装成 `.sql`；不携带凭据/敏感样本。

## 7. 构建方式概述（short）

`finance-data-qc/SKILL.md` 改为**两阶段为纲**：阶段一（探索与试探性检测，对应"发现并定级"子流程）必走；阶段二（甄别固化与策略设计，对应"固化与设计"子流程）条件触发。阶段一复用五阶段漏斗并补互斥归属纪律，阶段二新增甄别门（三问）与"固化基准 = 可复算"，把 schedule/threshold/alert_on/depends_on 落到 `deliverables.md` 的 `checks/` 结构与 `few-shots.md` 示例；`defect-catalog.md` 第 10 类补"甄别门"表述。改动集中在 `finance-data-qc` 内部（SKILL + deliverables + defect-catalog + few-shots），不动其他 skill、不新增测试目录。

## 8. 开放风险

- **两阶段使流程变长/节奏变慢** → 阶段二只有甄别 + 策略设计，是轻量筛选，不是重流程；验收时间主要仍在阶段一。
- **甄别门被形式化走过场** → 三问必须落到具体输出（复发风险评估、静默成本影响面、检测成本估算），不问清不固化。
- **可复算基准过于严格阻塞固化** → 允许"需先补契约"作为过渡标注，不把"现在不能复算"当成"永不固化"。
- **schedule 跟随制度缺默认值** → 制度未确认时 schedule 显式 `null`，不套默认日频（与契约纪律一致）。
- **与既有 few-shots 冲突** → 例 2"该检查应落为常驻校验"的措辞升级为"过甄别门后固化"，保持示例一致。
